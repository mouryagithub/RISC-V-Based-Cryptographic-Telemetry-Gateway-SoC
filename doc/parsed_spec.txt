RISC-V Based Cryptographic Telemetry Gateway SoC
System Architecture, Signal Interface, Memory Map, Subsystem Register, and Functional Specification
Document Version: 2.0 (Consolidated Technical Specification)  |  Core Architecture: Western Digital VeeR-EL2 (RV32IMC)  |  Interconnect: 64-bit AMBA AXI4 Crossbar  |  Date: November 2026

1. Introduction
===============

1.1 Problem Statement & Background
==================================
Modern embedded telemetry systems in aerospace, industrial automation, and defense applications require real-time, deterministic data ingestion coupled with rigorous cryptographic verification and encryption. When high-bandwidth telemetry streams are ingested, executing high-bandwidth stream hashing (SHA-256 for message authentication and integrity verification) and block cipher transformations (AES-256 CBC for confidentiality protection) entirely in software on a 32-bit RISC-V core consumes substantial processor execution cycles. This software compute bottleneck causes substantial processing latency, degrades real-time interrupt response, and limits achievable telemetry ingress throughput.

1.2 Purpose of the SoC
======================
The Cryptographic Telemetry Gateway SoC is a custom System-on-Chip architected to offload bulk data movement and cryptographic compute overhead entirely from the central processor core. By combining an open-source 32-bit Western Digital VeeR EL2 RISC-V processor core (RV32IMC) with an autonomous 64-bit Direct Memory Access (DMA) controller, a shared 64 KB System SRAM frame buffer, and dedicated hardware accelerators for SHA-256 and AES-256, the SoC enables hardware-accelerated telemetry ingestion, integrity hashing, and payload encryption with minimal CPU intervention.

1.3 Key Architectural Objectives
================================
Design Highlight: The architecture cleanly decouples the 64-bit high-speed burst data planes (System SRAM, DMA engine, and Cryptographic FIFO endpoints) from the 32-bit peripheral control planes, ensuring that register configurations never bottleneck active high-bandwidth DMA cryptographic pipelines.

4.2 System SRAM Memory Map & Partitioning (64 KB)
=================================================
The 64 KB System SRAM (0x0000_0000 – 0x0000_FFFF) serves as the primary on-chip staging area, decoupling external low-speed ingress/egress from multi-megabyte cryptographic compute engines. It is partitioned into four dedicated 16 KB functional regions:

Address Range | Size | Buffer Function | Firmware Allocation & Operational Usage
0x0000_0000 – 0x0000_3FFF | 16 KB | Telemetry Ingress Buffer | Raw incoming telemetry packet frames transferred from UART RX FIFOs by CPU/DMA.
0x0000_4000 – 0x0000_7FFF | 16 KB | Cryptographic Staging Buffer | Pre-processed plaintext staging and destination for decrypted/encrypted AES payloads.
0x0000_8000 – 0x0000_BFFF | 16 KB | SHA-256 Scratchpad | Pre-padded message blocks (512-bit multiples) for hardware SHA digest verification.
0x0000_C000 – 0x0000_FFFF | 16 KB | Telemetry Egress Buffer & Descriptors | Finalized encrypted ciphertext packets awaiting serial transmission, and DMA descriptor memory.

5. Subsystem Register Specifications
====================================

5.1 AES-256 Cryptographic Accelerator (Base: 0x4000_0000)
=========================================================
The AES-256 accelerator performs high-speed block encryption and decryption adhering to FIPS-197. It implements a 14-round transformation pipeline with autonomous Cipher Block Chaining (CBC) feedback logic, 256-bit key expansion, and 128-bit Initialization Vector (IV) register integration.

Offset | Register Name | Width | Type | Reset Value | Field Descriptions & Functional Purpose
0x00 | AES_CTRL | 32-bit | R/W | 0x0000_0000 | [0]  start : Write 1 to start cipher operation. [1]  enc_dec : 0 = Encrypt, 1 = Decrypt. [2]  cbc_mode : 1 = Enable CBC mode (IV chaining), 0 = ECB mode. [3]  key_len : 1 = 256-bit key (14 rounds), 0 = 128-bit key (10 rounds). [4]  irq_en : 1 = Assert  aes_irq  on completion. [5]  soft_rst : Write 1 to reset internal state and FIFOs.
0x04 | AES_STATUS | 32-bit | RO | 0x0000_0000 | [0]  busy : High while round transformations are in progress. [1]  done : Asserted when all blocks in  AES_BLK_CNT  finish. [2]  key_ready : Key expansion schedule complete. [3]  err : FIFO overrun or illegal configuration detected.
0x08 | AES_BLK_CNT | 32-bit | R/W | 0x0000_0001 | [15:0]  block_count : Total number of 128-bit blocks to process in active burst.
0x0C | AES_IRQ_CLR | 32-bit | WO | 0x0000_0000 | [0]  irq_clr : Write 1 to clear  done  status flag and de-assert  aes_irq .
0x10–0x2C | AES_KEY0–7 | 8×32 | WO | 0x0000_0000 | 256-bit Cipher Key: KEY0 (bits [31:0]) through KEY7 (bits [255:224]).
0x30–0x3C | AES_IV0–3 | 4×32 | R/W | 0x0000_0000 | 128-bit Initialization Vector: IV0 (bits [31:0]) through IV3 (bits [127:96]).
0x40–0x4C | AES_DIN0–3 | 4×32 | WO | 0x0000_0000 | 128-bit Direct Plaintext Input Register (AXI-Lite CPU direct access bypass).

6. Control Path and System Coordination
=======================================

6.1 System Control Topology
===========================
The control path defines how the Western Digital VeeR EL2 core orchestrates system operations across the unified AXI4/AXI4-Lite interconnect architecture. Both high-throughput data movement and peripheral control-plane register configurations are carried over the 64-bit AXI4 crossbar. Peripherals with lightweight register interfaces are connected via AXI4-Lite subordinate ports through protocol bridges.
Downward Configuration Flow: Control transactions originate from the VeeR EL2 Core through its Load/Store Unit (LSU) master interface across the 64-bit AMBA AXI4 interconnect directly to the AXI4-Lite slave interfaces of individual peripherals and accelerators (Timer at 0x4000_2000, UART at 0x4000_1000, GPIO at 0x4000_3000, DMA at 0x4000_5000, SHA-256 at 0x4000_4000, and AES-256 at 0x4000_0000).
Upward Event Flow: Hardware event notifications flow upward from these endpoints into the Programmable Interrupt Controller (PIC), which asserts the VeeR EL2 core's external interrupt vector (extintsrc_req). This triggers the execution of the corresponding Interrupt Service Routine (ISR), followed by status register readback, event clearance via write-1-to-clear registers, and resumption of background execution.

7. Data Path and Telemetry Pipeline Flow
========================================

7.1 Data-Path Overview
======================
[Ingress Path] External Host ──► Serial Line ──► UART ──► AXI4-Lite ──► VeeR EL2 Core ──► AXI4 ──► System SRAM [Data Movement & Processing] System SRAM ──► AXI4 ──► DMA Controller ──┬──► SHA-256 ──► Digest ──► AXI4-Lite / CPU Readback │ └──► AES-256 CBC ──► Ciphertext ──► System SRAM [Egress Path] System SRAM ──► VeeR EL2 (LSU) ──► AXI4-Lite ──► UART ──► Serial Line ──► External Host
The data path consists of two cryptographic processing branches. The SHA-256 branch produces an integrity digest, while the AES-256 CBC branch produces the encrypted payload. The architecture does not assume that the SHA-256 output is directly connected to the AES-256 input unless such a dependency is explicitly defined by application firmware. The DMA controller executes the required transfers between System SRAM and the respective cryptographic accelerator interfaces. The SHA-256 and AES-256 paths are independent processing branches and can operate concurrently or sequentially as scheduled by system firmware.

7.2 Data Ingress
================
Ingress Source: The data path begins at the external host, which supplies raw telemetry payloads, configuration frames, or command streams across the asynchronous serial communication line.Ingress Interface: The physical UART controller receives the serial data stream, converts serial frames into parallel bytes, and buffers incoming bytes into its internal 16-byte receive holding FIFO accessible via the UART's AXI4-Lite control interface.Transport Mechanism: The VeeR EL2 core retrieves received data from the UART controller through memory-mapped register accesses over the AXI4 interconnect via the UART's AXI4-Lite slave interface, or alternatively delegates fixed-source streaming to the DMA controller.Initial Storage Destination: The core issues write transactions through its AXI4 LSU master interface across the 64-bit crossbar to deposit incoming telemetry bytes directly into the System SRAM Ingress Frame Buffer (0x0000_0000 – 0x0000_3FFF), establishing the base payload for subsequent cryptographic processing.

7.3 SRAM as the Shared Data Buffer
==================================
Buffer Role: The 64 KB System SRAM serves as the primary on-chip staging area and memory-mapped repository where raw telemetry payloads, intermediate processing blocks, and final encrypted outputs reside.Interface Access: Both the VeeR EL2 core via its LSU interface and the DMA controller access the SRAM as central memory slaves over the 64-bit AMBA AXI4 interconnect.Functional Purpose: It decouples the ingress and egress routines from high-speed cryptographic and transfer operations by providing stable, addressable memory ranges.Operational Boundary: The SRAM provides addressable storage for telemetry payloads, intermediate data, and encrypted results accessed through the AXI4 crossbar.

7.5 SHA-256 Data Path
=====================
Data Source: Buffered plaintext telemetry blocks residing in System SRAM.Transport Mechanism: The DMA controller streams these blocks across the AXI4 interconnect directly into the SHA-256 accelerator data FIFO endpoint.Processing Operation: The hardware accelerator computes the cryptographic message digest entirely through dedicated internal logic without modifying the underlying data blocks in SRAM.Result Destination: The resulting 256-bit hash digest is held in internal accelerator result registers (SHA_DIGEST0–7 at 0x4000_4020–3C), from which it is retrieved by the processor through the accelerator's control interface.

7.6 AES-256 Data Path
=====================
Data Source: Plaintext telemetry payload blocks stored within System SRAM.Transport Mechanism: The DMA controller reads and streams the plaintext blocks over the AXI4 interconnect into the AES-256 CBC engine data interface.Processing Operation: Operating in Cipher Block Chaining mode, the engine combines incoming plaintext blocks with an Initialization Vector (IV) and a pre-loaded 256-bit key, chaining ciphertext dependencies across sequential transformation cycles.Result Destination: The resulting encrypted ciphertext blocks are written back across the AXI4 interconnect and stored in the designated Egress Buffer (0x0000_C000 – 0x0000_FFFF) within System SRAM.

7.7 Data Egress
===============
Egress Source: Finalized, encrypted payload blocks residing within the System SRAM result buffers.Transport Mechanism: Under firmware direction, the VeeR EL2 core reads the secured payload from SRAM using its AXI4 LSU interface and directs it toward the UART transmit registers via the AXI4 interconnect through the UART's AXI4-Lite slave interface.Processing Operation: The UART controller accepts the bytes through AXI4-Lite register writes and serializes the data stream according to pre-configured baud rates and frame formats.External Destination: The serialized ciphertext leaves the SoC pins across the uart_tx pin to reach the external host or telemetry ground station.

9.2 Reset Strategy
==================
The SoC boundary receives an active-low asynchronous reset (aresetn). An internal reset synchronizer bridges this signal into the clk domain to provide clean synchronous de-assertion. An internal inverter derives active-high reset rst = ~aresetn to drive the axi_interconnect core, ensuring glitch-free power-on sequencing across all crossbar channels.
